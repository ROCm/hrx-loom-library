# Qwen3.8 text-service policy

The dense Qwen3.8 and Flash-Next compositions share chat framing, sampling
options, and queued text execution. The providers expose Loom's text-service
v1 exports; each composing model supplies `text_model_name_v1`, its tokenizer,
preparation, and numerical stages. The program chooses no physical device and
contains no checkpoint paths.

## Service ownership

The host service calls three separate providers around each queued epoch.
Their boundary is storage ownership and completion, independent of the model's
proposal algorithm or numerical stages.

| Provider | Inputs and ownership | Result |
| --- | --- | --- |
| `encode` | Validated ownership events, host plans, and retained host packet storage. `text_encode_state_v1` updates resident origins; `text_encode_epoch_v1` packs the first and continuation cohorts. | Borrowed, exact upload ranges. The caller retains their backing until transfer completion. |
| `epoch` | Prepared stage IDs and retained device bindings. `text_step_v1` submits an isolated step; `text_epoch_v1` composes proposal, verification, and accepted-state catch-up for one or two cohorts. | Work completion. Feedback transfer has its own completion and can overlap catch-up. |
| `publish` | Immutable completed feedback banks, their original host plans, and caller-owned progress arrays. `text_publish_epoch_v1` resolves continuation owner tags. | Consumed/output counts, accepted tokens, source positions, and actual proposal counts in original-request order. |

```text
host plans --encode--> retained host packets --uploads--> device stages
                                                           |
                                             verification / acceptance
                                                /                  \
                                       feedback transfer       draft catch-up
                                                \                  /
                                          caller joins completion
                                                    |
                                                 publish
                                                    |
                                            request progress
```

Encoding and publication contain no runner calls. Execution does not encode
host packets or interpret neural-network weights. The native caller owns
admission and lifetime joins; `speculation` selects the prepared proposal and
verifier pair from source-owned policy. Composing models include all three
providers explicitly. Each provider's existing service export signatures remain
the linking contract.

`publish.cxx` implements publication using the shared
[`EpochPublication`](../publication.h) argument record. The importer flattens its
members into the native v1 signature, so existing Loom callers and tests consume
the same ABI. Feedback origins and packed counts remain calls to the shared
Qwen feedback motif. The provider imports once into bytecode; source publications
carry its declared header, while bytecode publications omit compiler-only inputs.

## Chat and retained history

`chat.loom` consumes the native service's request records and its
JSON, tokenizer, input-validation, and tool host imports. It owns the ChatML
framing, optional reasoning block, XML tool syntax, media markers, and sampling
packet. Generated text becomes reusable retained history only when canonical
history preserves the exact emitted bytes. Partial reasoning and tool markers
remain withheld during streaming and are resolved at completion. Returned
buffers have VM ownership; request-local scalar state remains opaque to the
service caller.

Completion receives the native stop cause. A token-limit stop omits an unfinished
XML tool call while preserving preceding complete calls, content, and reasoning;
it remains a `length` completion. Malformed framing still fails, including at a
token limit. Canonical history excludes the unfinished call, so its mismatch
with the generated bytes prevents retained device-state reuse.

The model has one leading instruction envelope. Chat requests may spell that
role `system` or `developer`; both render the same Qwen system tokens. A second
instruction message or one after user/assistant history is rejected, since the
checkpoint template has no corresponding role or priority boundary.

`reasoning_effort` selects the checkpoint's trained prompt policy: `none` closes
the thinking prefix, `low` requests brief reasoning, `medium` opens thinking
without an extra instruction, and `xhigh` requests careful reasoning. The common
client values `minimal`, `high`, and `max` alias `low`, `xhigh`, and `xhigh`,
respectively; they do not introduce additional token budgets. Omitting both
thinking controls keeps reasoning off. `enable_thinking=true` alone retains the
checkpoint's xhigh policy. Explicit effort and enable/disable controls must
agree. The sampling packet and device execution are independent of this prompt
selection.

The cold `text_chat_reasoning_v1` declaration advertises `none`, `low`, `medium`,
and `xhigh` for model discovery, with `none` as the omission default. Accepted
aliases do not appear as distinct trained policies in the client selector.

`preserve_thinking` defaults to true. False removes thinking envelopes from
completed exchanges while keeping them in the current tool cycle, independently
of whether the next response enables reasoning. User-form `<tool_response>`
wrappers continue the current cycle; an ordinary user message starts a new one.
Both plain and ordered multimodal content use this boundary. The optional
history scan follows ranges in the original request without copying history or
image payloads, and normal preserving requests skip that scan.

`chat_template_kwargs` consumes the same three controls. Top-level, nested,
and repeated values must agree after effort alias resolution; member order
never overrides an explicit preference. Unused keywords do not affect the
template. The policy checks the types and values of controls it consumes.

Nullable request controls inherit the omission defaults. This includes
`enable_thinking`, `reasoning_effort`, `preserve_thinking`, and
`chat_template_kwargs`: a null control does not conflict with an explicit
top-level or nested value. A null `model_options` leaves the image budget at its
default.

Sampling consumes `temperature`, `top_p`, `top_k`, and `seed`. Request nulls
preserve the deployment's sampling defaults, including an explicit default
seed; otherwise the normal request nonce supplies the seed. Deployment sampling
configuration remains strict. Invalid numeric values and duplicate sampling
members are rejected before admission.

Other client fields pass through without adding generation behavior. In
particular, this policy does not implement `stop`, presence/frequency penalties,
or `response_format` constraints. The server's
[HTTP profile](https://rocm.github.io/hrx-system/loom/serving/http-profiles/#request-compatibility)
documents native controls, nullable defaults, and accepted compatibility fields.

Tool declarations are prompt data, not an execution allowlist. The string
`tool_choice: "none"` suppresses the tool token through the model's sampling
packet without changing retained history. The policy does not validate tool
permissions or argument schemas, and named or required choices do not imply a
constrained-generation guarantee. Generated calls are translated for the client
to interpret and execute.

Queued execution separates packed cohort position, resident row, source
position, and first-cohort policy identity. Preparation owns the retained
control allocation; packet encoding returns only live upload ranges. Resident
growth preserves stage handles and existing sampling policies without deriving
packet capacity from the resident count.

Token and request-span capacities come from separate columns of the prepared
shape catalog. Token capacity sizes input packets; span capacity sizes feedback
and fixes its two bank offsets. Live counts determine the records written and
consumed. The queued bank packs owner tags immediately after its live records,
so the host can download the admitted request bound without another count
readback. Unused feedback requires no initialization and is never consumed.

Shared storage writers describe allocations and row views in caller-owned
tables. Model preparation computes extents, and the native materializer owns
the actual allocations. Each source documents its record layout and update
contract; descriptor-only tests cover large extents without creating payloads.

Runner imports enqueue target, proposal, verification, catch-up, and feedback
work. Completion edges determine when mutable work has retired and when
immutable feedback may be published. Continuations preserve their first-cohort
owner while compacting live rows. Neither policy transforms nor packet writers
wait for a device or infer ownership from buffer contents.

The shared epoch calls `qwen38.epoch.target` after proposal and before feedback
and predictor catch-up. A model links one provider with its stage catalog and
buffer layout. `epoch_dispatch.loom` supplies the ordinary single-command target
and verifier paths. A model-specific provider can split that target computation
around asynchronous input readiness while retaining the shared packet encoding,
speculation selection, feedback, and continuation policy. The returned completion
must cover target outputs and accepted-state publication.

Each verified epoch brackets proposal and target execution with three ordered
queue-clock captures. The samples share the normal feedback banks and retire
before publication, so observing them adds no host wait or separate readback.
The shared feedback header also carries the work actually executed: neural
inputs per proposal step, verification-width counts, known inputs, context
extent, logical causal query/key pairs, and selected executable capacities.
Lookup-satisfied rows contribute no neural work, and the parallel drafter
reports one block-processing step. These counts describe logical work rather
than measured memory traffic. Raw ticks use the runner's clock frequency and
valid-bit width.

Acceptance follows each span's actual anchor-plus-draft length within the
compiled verification ceiling. Different spans can therefore stop drafting at
different widths without reading unused candidate slots. The completed
publication callback receives the model's retained control state alongside
both immutable feedback banks. Measurements do not themselves change proposal
selection.

`speculation.loom` consumes an optional model-prepared catalog of shorter
proposal/verifier pairs. Each record supplies its verification width and both
program identities; the composing model owns the cost policy. The configured
depth remains the reservation ceiling. Selection inspects the live host plan,
compacts generated spans to the chosen width, and keeps both queued banks on
the same pair. Final ordinary decodes preserve their one-token spans beside
proposing peers. Prefill, media, supplied candidates, and cohorts outside the
catalog use the ordinary prepared stages. No request-time compilation, device
readback, weight copy, or extra synchronization is involved. The catalog occupies
48 host bytes per model and survives resident growth without entering newly
admitted sampling rows.

`chat_media.loom` plans and renders ordered images and timestamped video frames.
Native inspection supplies decoded dimensions, source ranges, and finite,
nondecreasing timestamps; source selects temporal pairs, geometry, marker ranges,
and token counts. Each video pair emits its mean timestamp to one decimal place
with nearest-even rounding, followed by its video feature tokens. An odd tail
aliases its final frame instead of duplicating pixels. Requests may contain up
to 768 images/frames within the existing compressed-byte and context budgets.
The HTTP boundary accepts vLLM-compatible `video_url` JPEG sequences and
`media_io_kwargs.video` timing. Explicit frame sampling is preserved; container
decoding is not a dependency.

`media.loom` fills eight-word mixed-input records and tracks compressed spatial
positions. Each projection's extent comes from the prepared source geometry
and native invocation packet, independently of resident session capacity.
Compaction preserves feature offsets into the original immutable packet.
`vision_geometry.loom` evaluates smart resize on the integer grid of 32-pixel
merged patches. Images use the requested token budget; videos use the checkpoint's
whole-clip pixel budget, raw frame count for scaling, and nearest-even temporal
alignment for the area threshold. Short-axis expansion can produce a 6,400-pixel
output axis without increasing the 4,096-pixel source decode limit. Linking chat
policy alone does not supply an encoder.

The image-service providers share the native multi-plane packet and completion
protocol. `vision_pixels.loom` constructs antialiased bicubic axis plans for each
distinct RGB/RGBA plane and preserves its orientation. `vision_stages.loom` binds
height, width, plane count, and cohort size to the composing model's
`qwen38_vision_projector` command. The prepare host owns stage compilation and
reuse. `vision_prepare.loom` binds the `vision` parameter scope through the
model's `weights.loom` placement policy and returns exact service ceilings.
The model supplies its name and feature width.

`vision_control.loom` tags compatible projections, consumes the native packer's
canonical directory, describes disjoint F32 feature ranges, and hands execution
to the runner. Cohort admission accounts for both patch rows and prepared upload
bytes. Compatible projections share linear and feed-forward weight reads while
attention stays within each image or frame pair. Forecasting uses the same
workspace query as the device command and includes retained features plus one
shared output root. Native serving keeps those roots alive until their consumers
finish. These providers add no extra upload copy or completion wait.

The [tests](test/) use the real native chat caller, small tokenizers, and VM
checks for source-defined packet and streaming contracts. Learned service
checks in each model qualify the numerical stages and complete device lifetime.
