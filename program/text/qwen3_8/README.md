# Qwen3.8 text-service policy

The dense Qwen3.8 and Flash-Next compositions share chat framing, sampling
options, and queued text execution. The providers expose Loom's text-service
v1 exports; each composing model supplies `text_model_name_v1`, its tokenizer,
preparation, and numerical stages. The program chooses no physical device and
contains no checkpoint paths.

`chat.loom` consumes the native service's validated request records and its
JSON, tokenizer, input-validation, and tool host imports. It owns the ChatML
framing, optional reasoning block, XML tool syntax, media markers, and sampling
packet. Generated text becomes reusable retained history only when canonical
history preserves the exact emitted bytes. Partial reasoning and tool markers
remain withheld during streaming and are resolved at completion. Returned
buffers have VM ownership; request-local scalar state remains opaque to the
service caller.

Completion receives the native stop cause. A token-limit stop omits an unfinished
XML tool call while preserving preceding complete calls, content, and reasoning;
it remains a `length` completion. Malformed framing still fails, including at a
token limit. Canonical history excludes the unfinished call, so its mismatch
with the generated bytes prevents retained device-state reuse.

The model has one leading instruction envelope. Chat requests may spell that
role `system` or `developer`; both render the same Qwen system tokens. A second
instruction message or one after user/assistant history is rejected, since the
checkpoint template has no corresponding role or priority boundary.

`reasoning_effort` selects the checkpoint's trained prompt policy: `none` closes
the thinking prefix, `low` requests brief reasoning, `medium` opens thinking
without an extra instruction, and `xhigh` requests careful reasoning. The common
client values `minimal`, `high`, and `max` alias `low`, `xhigh`, and `xhigh`,
respectively; they do not introduce additional token budgets. Omitting both
thinking controls keeps reasoning off. `enable_thinking=true` alone retains the
checkpoint's xhigh policy. Explicit effort and enable/disable controls must
agree. The sampling packet and device execution are independent of this prompt
selection.

The cold `text_chat_reasoning_v1` declaration advertises `none`, `low`, `medium`,
and `xhigh` for model discovery, with `none` as the omission default. Accepted
aliases do not appear as distinct trained policies in the client selector.

`preserve_thinking` defaults to true. False removes thinking envelopes from
completed exchanges while keeping them in the current tool cycle, independently
of whether the next response enables reasoning. User-form `<tool_response>`
wrappers continue the current cycle; an ordinary user message starts a new one.
Both plain and ordered multimodal content use this boundary. The optional
history scan follows ranges in the original request without copying history or
image payloads, and normal preserving requests skip that scan.

`chat_template_kwargs` accepts the same three controls. Top-level and nested
values must agree after effort alias resolution; member order never overrides
an explicit preference. Unknown keys, duplicate members within one object, and
wrongly typed values reject.

Queued execution separates packed cohort position, resident row, source
position, and first-cohort policy identity. Preparation owns the retained
control allocation; packet encoding returns only live upload ranges. Resident
growth preserves stage handles and existing sampling policies without deriving
packet capacity from the resident count.

Shared storage writers describe allocations and row views in caller-owned
tables. Model preparation computes extents, and the native materializer owns
the actual allocations. Each source documents its record layout and update
contract; descriptor-only tests cover large extents without creating payloads.

Runner imports enqueue target, proposal, verification, catch-up, and feedback
work. Completion edges determine when mutable work has retired and when
immutable feedback may be published. Continuations preserve their first-cohort
owner while compacting live rows. Neither policy transforms nor packet writers
wait for a device or infer ownership from buffer contents.

`chat_media.loom` plans and renders ordered images and timestamped video frames.
Native inspection supplies decoded dimensions, source ranges, and finite,
nondecreasing timestamps; source selects temporal pairs, geometry, marker ranges,
and token counts. Each video pair emits its mean timestamp to one decimal place
with nearest-even rounding, followed by its video feature tokens. An odd tail
aliases its final frame instead of duplicating pixels. Requests may contain up
to 768 images/frames within the existing compressed-byte and context budgets.
The HTTP boundary accepts vLLM-compatible `video_url` JPEG sequences and
`media_io_kwargs.video` timing. Explicit frame sampling is preserved; container
decoding is not a dependency.

`media.loom` fills eight-word mixed-input records and tracks compressed spatial
positions. Each projection's extent comes from the prepared source geometry
and native invocation packet, independently of resident session capacity.
Compaction preserves feature offsets into the original immutable packet.
`vision_geometry.loom` evaluates smart resize on the integer grid of 32-pixel
merged patches. Images use the requested token budget; videos use the checkpoint's
whole-clip pixel budget, raw frame count for scaling, and nearest-even temporal
alignment for the area threshold. Short-axis expansion can produce a 6,400-pixel
output axis without increasing the 4,096-pixel source decode limit. Linking chat
policy alone does not supply an encoder.

The image-service providers share the native multi-plane packet and completion
protocol. `vision_pixels.loom` constructs antialiased bicubic axis plans for each
distinct RGB/RGBA plane and preserves its orientation. `vision_stages.loom` binds
height, width, plane count, and cohort size to the composing model's
`qwen38_vision_projector` command. The prepare host owns stage compilation and
reuse. `vision_prepare.loom` binds the `vision` parameter scope through the
model's `weights.loom` placement policy and returns exact service ceilings.
The model supplies its name and feature width.

`vision_control.loom` tags compatible projections, consumes the native packer's
canonical directory, describes disjoint F32 feature ranges, and hands execution
to the runner. Cohort admission accounts for both patch rows and prepared upload
bytes. Compatible projections share linear and feed-forward weight reads while
attention stays within each image or frame pair. Forecasting uses the same
workspace query as the device command and includes retained features plus one
shared output root. Native serving keeps those roots alive until their consumers
finish. These providers add no extra upload copy or completion wait.

The [tests](test/) use the real native chat caller, small tokenizers, and VM
checks for source-defined packet and streaming contracts. Learned service
checks in each model qualify the numerical stages and complete device lifetime.
